## 二、逐日记录

### 10-19 · 先做场景，不先做功能

起点不是「做一个医疗系统」，而是先验证一个交互想法：把网页做成一片草地，
用户的鼠标位置决定镜头朝向，进出页面有转场。这一版没有任何业务逻辑，
纯粹是场景可行性验证——如果 3D 场景在浏览器里跑不顺畅，后面所有交互设计都要换。

### 10-20 · 从场景转向产品

用同一套场景改造成「毛绒球医生」：会看向鼠标、会说话、会跟随滚动位置。
当天完成三件事：

1. **定位确定**：面向普通家庭的用药提醒与健康档案，不做面向医生的专业系统。
   理由是家庭场景的痛点更具体——多个人同时吃药、老人记不住、家属不清楚今天吃没吃。
2. **品牌更名**：项目代号统一为 MedAI。
3. **全栈化**：按规格实现多患者 AI 辅助问诊的后端与数据模型，接上前端视觉。
4. **形象改版**：绒球医生改为小白兔（参考三只玩偶图中最左一只的造型）。

这一天留下的关键判断：**先有形象，再有功能**。后续所有功能入口（问诊、打卡、科普）
都挂在同一个场景上，而不是各开一个页面。

### 10-22 · AI 真正接进来

上午还是本地模板回复，当天完成三条关键升级：

- **接入 DeepSeek 真实 API**，替换本地模板。这一步是全项目最重要的技术决策，
  选型理由写在技术文档第 4 章：不微调、不自建推理服务，用通用模型 + 结构化提示词，
  因为医疗科普场景需要的是「说人话 + 守住边界」，而不是专科诊断能力。
- **聊天记录不永久保留**：只保留原始对话 30 天，「小结」「结论卡片」「患者档案」不受影响。
  这是有意的隐私设计，不是技术限制。
- **支持上传资料给 AI 看**：用户可以把药品说明书拍照上传，作为对话上下文。

同时上线主页三个入口、疾病科普库（90 种疾病）与药品说明查询（73 种药品）。

当天还排查了一个真实故障：网站「打不开」。根因不是代码，而是运行环境的端口与进程残留。

### 10-23 · 气泡是交互，不是装饰

给兔子加对话气泡，过程中做了三个判断：

1. **只做文字，不做语音**——语音会增加噪声与隐私负担，家庭场景里文字更可控。
2. **注视要跟手**：最初的注视是插值到鼠标位置，看起来「僵」；改为按屏幕坐标换算后自然很多。
3. **气泡不能压住问诊按钮**：这是当天最后一轮才发现的遮挡问题，属于布局而非逻辑缺陷。

### 10-24 · 细节决定可用性

- 蒲公英被渲染出「根」，用户截图反馈后重写生成函数。
- 从科普库返回首页会重放开场动画，改为按会话状态判断。
- 场景退出编辑后复用实例，解决来回切换卡顿。
- 补上手机号验证码登录，为真实用户注册打通路径。

### 10-26 · 医疗能力落地

这一天是功能密度最高的一天，也是产品从「好看」变成「有用」的转折：

- **今日用药木牌**：把「今天谁要吃什么药」直接放在草地上，不用点进档案。
  同一天修掉一个会当场翻车的 bug：漏服计数在跨天时算错。
- **红旗拦截**：11 条规则识别「胸痛、呼吸困难、意识改变、大出血」等必须就医的信号，
  命中后停止 AI 问诊，直接给出就医建议。这是 AI 安全可控的核心实现——
  **宁可少答，不能误导**。
- **就诊摘要**：把家庭记录整理成医生看得懂的一页纸，可打印 A4。
  解决的是「家属说不清病情」这个真实痛点。

### 10-27 · 视觉推倒重来一次

木牌先做成立面 3D 木板 + HTML 文字层，效果不满意，改成「吊牌」（带挂绳、会轻微摆动）。
同一天知识库扩容一倍并补配图。

**这一天的价值不在于做成了什么，而在于推倒重来的成本足够低**：
场景、UI、数据层是分开的，换一层视觉不用动业务逻辑。

### 10-28 · 打卡闭环

用户提出「点木板就能打卡，不用再进档案」。改动看似小，实际牵动四层：

- 新增 `GET /api/medications/board`，专供打卡后重新拉取（与「此刻弹不弹通知」的接口分开）。
- 3D 板面文字要随打卡实时变化。
- **卡片行序冻结**：板子按「谁还没吃」排序，打卡会让它现场重排，手指点下去那行会换人。
  打开卡片那一刻冻结顺序，才能连点。
- 写 8 项断言自检，其中「卡片底部不越界」这条当场抓到了一次 923 > 900px 的溢出。

### 10-29 · 从「能跑」到「能交」

上午收尾打卡（修复窗口 resize 后木牌停在半空），下午转向交付：

- 全面体检：补齐 404 与错误兜底页、登录页演示账号入口、8 项入口自检脚本。
- **建立 Git 仓库**，按功能模块切分为 25 次提交（详见第三节说明）。
- 重写技术文档为七段式，22 页，含 AI 选型取舍与创新点分类。

### 10-30 · 合规与可交付

补全团队信息；修掉一个有隐蔽性的部署问题：生产模式下会话 cookie 带 `Secure` 标记，
用局域网 IP 明文访问时浏览器会丢弃，表现为「密码对却退回登录页」；
同时修正 `tsconfig` 把打包产物纳入编译导致的类型报错；启动脚本改为首次运行自动建库灌数据。

### 11-13 · 交付之后仍在迭代

新增管理员后台（数据看板、患者管理、问诊记录、系统配置与安全四组控制台）
与用户反馈闭环（用户提交、后台回复、操作落审计日志），共改动 47 个文件。
平台名称改为后台可配置、全站生效；图片对话切换视觉模型以支持原图。

这一条的意义在于：**项目没有停在比赛节点上**。

## 三、关于 Git 提交时间的说明

代码开发自 10-19 起在本地持续进行，Git 仓库于 10-29 为满足提交要求统一建立，
随后按功能模块回溯切分为 30 次提交。因此仓库中的提交日期集中在 10-29 至 10-30，
并不等同于开发工期。

这样处理的取舍：

- **没有把提交时间改到更早的日期**。仓库创建时间在 GitHub 上是公开的（10-29），
  任何早于它的提交时间都会自相矛盾；伪造时间线一旦被追问就失去全部可信度。
- **提交粒度按「一个提交对应一个可回滚的功能单元」切分**，
  而不是按文件或按时间平均切，这样每个提交都能读懂、能单独 review。
- **开发过程以本文件为准**，并可由仓库内的设计文档、实机截图、自检脚本交叉验证。
