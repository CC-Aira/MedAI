01　项目概述

1.1 作品简介

MedAI 面向"一个家里谁在管药"这件事。它把家庭成员的档案、在服药物、问诊记录、就诊摘要 收在一个账号里，用一片可以点开的 3D 草地作为入口：家里每个人是一块小牌子，点开就能对话； 天上吊着一块木板，写着全家今天吃了几次药，点一下就能打卡。

产品的边界写得很清楚：不做诊断、不开处方、不替用户判断"哪句话重要"。 AI 只承担三件事 —— 把专业术语翻译成人话、把散落的信息整理成可执行的动作、 把一次问诊整理成一张能带去医院的纸。判断权始终在患者手里。

除用户端外，作品还包含一套平台管理员后台（数据看板、患者管理、问诊记录、 AI 模型配置、系统参数、公告与操作日志）和一条用户反馈闭环 （用户在"我的"页提交意见，管理员在后台处理并回复，全流程落审计日志）。 管理员只能看到统计口径与问诊摘要，看不到对话原文 —— 管理权与隐私边界同时成立。

1.2 背景与意义

中国有超过 3 亿的慢性病患者，其中相当一部分是老年人；与此同时，"一个家庭里谁在管药"这件事， 通常落在家里那个二三十岁的年轻人身上。他要记得父母各吃什么药、哪天该复诊、孩子发烧到多少度该去医院， 还要在下班后替父母把"医生说的一堆话"翻译成能执行的动作。

这件事的难处不在于信息不够，而在于信息散落在药盒、纸质病历、微信聊天记录和老人的记忆里。 家里老人吃几种药，子女往往说不全；上一次问诊医生说了什么，一周后基本只剩一句"多喝水"。

现有工具为什么没解决

现有形态它做到的它缺的
手机闹钟 / 药盒提醒器 到点响，便宜、可靠 只知道"该吃药了"，不知道"谁该吃、吃几片、吃没吃"；换个人就全乱
医院 App / 互联网医院 能挂号、能复诊、有电子病历 每家医院一套，跨院不通；面向"这一次就诊"，不面向"这一年"
通用 AI 聊天 什么都能问，门槛低 没有档案就没有个体化；不了解过敏史、在服药物，建议只能停在科普层面
健康管理类 App 功能齐全、数据维度多 要填的太多，老人用不了；界面像体检报告，看不下去

结论是：缺的不是功能，而是一个"全家共用、一个人维护、老人也看得懂"的容器。 这个容器还必须解决一个矛盾 —— 数据要共享（全家人看得到），隐私不能共享（别人一份都看不到）。

1.3 应用场景与目标用户

角色是谁他真正在意的一件事
主要使用者25–45 岁，家里管事的那个子女爸妈今天吃药了没有；孩子夜里发烧要不要去急诊
被照护者父母（多为慢病）、老人、儿童不想学新东西；只想知道"现在该干什么"
次要使用者异地子女、家庭护工不在身边也能看到今天的情况
平台运营者部署方的管理员（学校 / 社区 / 机构）知道平台用得怎么样、AI 答得准不准；出了问题能公告、能追溯

场景一：早上七点，厨房。手机在灶台边响了一声，兔子在草地上说"该给妈妈吃降压药了"。 用户腾不出手，就把手机架起来点了一下木牌上那一行 —— 打卡完成，板子上的 2/5 变成 3/5。 整个过程两个动作，不用进任何二级页面。

场景二：夜里十一点，孩子发烧。用户打开草地，点孩子的牌子问"39 度，一直哭，要不要去医院"。 系统先做本地红旗判断（有没有抽搐、意识不清、皮疹），再结合档案里的年龄体重和在服药物回答， 最后给出一张可以带走的就诊摘要。

场景三：复诊前一晚。用户点开"病程时间轴"，把这三个月发生的事排成一条轴： 哪天开始吃药、聊过几次、结论卡片写了什么。点"投影视图"，铺成一张白纸，截图或打印， 第二天直接给医生看 —— 不用再凭记忆复述。

三个场景都发生在手机上，而且经常是"一只手、几秒钟、注意力被打断"的状态。 这直接约束了设计：主操作必须在首屏一次点击内完成；文字要大到在油烟和昏暗里也能读； 动画必须能在中低端安卓机上跑得动（见 7.4 性能取舍）。

03　系统架构设计

3.1 总体架构

整体是"单页壳 + 服务端路由 + 一层 AI 适配"的结构。用户端浏览器侧只有一片草地和一个问诊面板， 状态集中在 MeadowStage.tsx；管理端是同仓库下的 /admin 控制台与 /me 个人中心；服务端 33 个 API 路由按 "校验输入 → 认门 → 查配置 → 干活"的固定顺序处理，任何一步不过就直接返回。

表现层

管理端：四组控制台（数据看板 / 患者管理 / 问诊记录 / 系统配置），Server Component 取数

04　AI 技术方案

4.1 选型理由

这一层是本作品权重最高的部分，也是做取舍最多的地方。三个选题决定了技术路线： 要不要微调、要不要向量库、要不要 Agent 框架。

（1）为什么用提示词个体化，而不是微调

微调适合"改变说话风格与任务格式"，不适合"让模型知道某个具体患者的过敏史"。 后者属于事实注入，用提示词就能做到，而且改了立刻生效 —— 患者今早刚加的青霉素过敏，下午的对话就必须带上，微调模型做不到这个时效。 另外微调需要构建数据集并承担训练成本，一个家庭的数据量根本不支持。 所以路线是：通用模型 + 结构化事实装配 + 硬约束提示词。

（2）为什么检索用 BM25，而不是上向量库

科普库是 90 条疾病 + 73 种药品的短文本结构化条目，不是长文档。 这类语料的查询有两种：一种是"高血压""阿莫西林"这种直接点名的， 另一种是"吃了这个药能不能喝酒"这种带着口语表述的。前者靠精确命中， 后者靠关键词共现 —— 两种都不需要"语义泛化"。

我们的做法是中文二元组（bigram）+ BM25 + 字段权重： 不引词典、不切词，按相邻两字切分（"高血压"→ 高血 / 血压）， 这恰好绕开了中文分词器最麻烦的歧义问题；病名与药名的权重是正文的 3 倍， 命中条目名即置顶；再叠一层别名映射（"烧心"→ 胃食管反流、"甲亢"→ 甲状腺功能亢进） 与全半角、简繁归一。零依赖、可解释、结果稳定 —— 同样一句问法， 今天和明天的检索结果一样，这在医疗语境里比"偶尔更聪明"重要。

检索结果不是整段塞进提示词：命中 3 条以内，每条只取标题、分类与三条要点， 并且在注入时编号，要求模型引用时写 [1]；回答末尾由代码 补一段"参考资料"，编号与注入时完全一致（见 4.4 的引用登记表）。 检索为空时不硬凑 —— 明确告诉模型"科普库没有覆盖，请说明这一点"，不让它拿常识冒充出处。

什么时候会上向量检索：条目涨到上千条，或者要检索用户上传的长文档 （病历 PDF、体检报告合集）时，会加一路 embedding 做混合排序。 现在上向量，是为了架构图好看而付一份几百 MB 的运行时依赖 —— 这与"离线可部署"这条非功能需求直接冲突。

（3）为什么自己写 Agent 循环，而不是套框架

前半句先承认必要：问诊确实需要"先查再说"。用户问"我今天吃药了吗"， 提示词里静态塞的用药列表可能已经过期；问"这个药和我妈吃的冲突吗"， 得先拿到她的在服药物才能比。这两类问题不查库就只能靠编。

后半句是取舍：不引 LangChain 这类框架。我们需要的只是 "模型返回 tool_calls → 执行 → 结果以 role=tool 回填 → 再问一次"这一个循环， 落在 lib/agent.ts 里不到 200 行，读得完、改得动、没有版本风险。 框架能省的是这 200 行，换来的是抽象层、回调协议与升级成本 —— 对 5 个只读工具来说不划算。

自己写就得自己定规矩，我们定了四条，全部写死在代码里：

  • 最多两轮。常见问题一轮就够（查用药 / 查科普），两轮覆盖"查药发现冲突、 再查那个冲突药"。再多是烧 token 换不来质量。
  • 决策轮不流式、temperature=0、maxTokens=200。这一轮只产出工具名和参数， 没必要逐字显示；参数必须稳定，不能让模型"发挥"出一个不存在的药名。
  • 失败即降级。上游 4xx（模型不支持 function calling）或网络抖动， 直接退回普通问答并记日志 —— 工具的缺席不该让这一轮问诊失败。
  • 只读。5 个工具全是查询，没有任何写操作。模型再怎么说"我帮你加一条用药"， 它也调不到写接口。

4.3 提示词工程

每次对话前拼五样东西：① 档案（年龄、体型、血型、过敏史、病史、习惯、主诉） ② 在服药物 ③ 最近 3 条问诊摘要 ④ 星标优先的 8 条结论 ⑤ 本轮 BM25 命中的 0~3 条科普条目（带编号，没有命中就整段不出现）。 前四块各自有 token 上限，总量恒定，不会随对话变长而失控； 超出上限时按"过敏史 > 主诉 > 在服药物 > 摘要 > 结论"的顺序裁剪，把最后的位置留给最重要的信息。

工具说明单独占一条 system 消息，与"正事"那段分开：决策轮带上它、正式作答的流式轮不带。 这样一来，正式回答的提示词和加工具之前逐字一致 —— 工具只影响"查什么"， 不影响"怎么说"，回归问题时能一眼分清是工具的锅还是提示词的锅。

医疗合规三件套永远在场：不下诊断、不开处方；过敏史优先考虑并主动提醒； 涉及处方药必须提示遵医嘱。这三条写在系统提示词最前面，并且不参与裁剪。

4.5 AI 安全与可控

（1）红旗症状不走模型

11 条规则覆盖胸痛、言语不清、抽搐、意识改变、大出血、呼吸困难、高热伴皮疹等急症表述。 命中即中断常规回答，改为固定话术要求立即就医或拨打 120。命中结果写进消息的 flag 字段（redflag.<kind>），刷新之后仍然是红的 —— 安全提示不能被一次页面刷新冲掉。

（2）AI 提建议，患者点头

模型只能返回候选事实（可补字段 / 新增用药 / 与档案冲突）。 其中 fill 与 add 默认勾选，conflict 默认不勾选并红色高亮， 必须患者亲手确认。冲突判定由代码完成，不交给模型 —— 让模型判断"新信息与档案是否矛盾"， 它容易顺着用户说。落库前每条都当不可信输入重新校验：字段白名单、长度上限、 单次 ≤ 20 条、medicationId 按 ownerId 重查。

一条自我约束：结论卡片（Note）不许自动生成。 客观事实可以让 AI 整理，但"哪句重要"是价值判断 —— 只有患者自己知道。 这个取舍让产品少了一个看起来很酷的功能，但保住了"判断权在人手里"这条线。

（3）管理端有三重边界

管理员能运营平台，但不能变成"偷看隐私的后门"。三条边界都写在代码里：

  • 权限：管理接口统一 requireAdmin() 守卫，注册接口强制 user 角色，接口层无提权入口； 停用的账号旧 Cookie 立即失效，重新登录返回 403。
  • 隐私：问诊记录页只展示症状输入与 AI 分析摘要，不提供对话原文入口 —— 管理员看得到"聊了什么主题"，看不到"原话怎么说的"。
  • 审计：停用 / 重置密码 / 改配置 / 发公告 / 处理反馈，每一个后台写操作都落 AdminLog，操作人、对象、详情可追溯。

4.6 MCP：把同一批工具交给外部客户端

对话里的 5 个工具，另外封装成一个 stdio 的 MCP server （scripts/mcp-server.ts，约 170 行）。用 MEDAI_MCP_USER=demo@medai.local npm run mcp 启动后， Claude Desktop / Cursor 这类客户端可以直接问"我妈今天吃药了吗"， 拿到的是同一份数据、同一套判定。

问题我们的答案
为什么不另写一套工具的 JSON Schema 只写一份：CONSULT_TOOLS 同时喂给模型和 MCP 客户端， 执行仍然走同一个 runTool()。两套实现迟早会漂移成"对话里能查、客户端里查不了"
身份从哪来stdio 是本机进程，用环境变量指定账号（MEDAI_MCP_USER）； 工具参数里可带 patient_name，不带就用该账号最早的档案
越权怎么办权限仍是 ownerId + patientId 两道，与 HTTP 接口同一套查询条件； stdio 不存在跨用户访问，谈不上把接口暴露到公网
能改数据吗不能。这一层只导出查询工具，不提供任何写操作 —— 外部客户端接进来也改不了患者的档案、用药和结论
做这一层的意义不在"多接一个客户端"。 它证明工具层是独立能力，不绑在自家聊天窗口上：工具的边界（只读、按人隔离、口径统一） 在两种调用方式下是同一份代码说了算，而不是各写一遍、各有一套判断。

5.2 视觉与交互基调

医疗类产品的默认语言是"白底 + 蓝 + 表格"，它传达的是准确，但也传达距离感。 MedAI 选择的是另一种可信：一片有风的草地、一只毛绒绒的绒球医生、一块手写的木板。 颜色取自清晨的草地（#8abfeb 的天空、#2f4a2b 的深绿、奶油色的纸面板）， 圆角与黏土质感的按钮（.clay）替代了直角卡片。 目的很实际：让人愿意在深夜打开它。

（1）开场：一株蒲公英

首次进入是一株 186 颗种子的蒲公英（内联 SVG，无图片请求）。吹散之后 3D 草地才显出来 —— 这不是装饰，是用 1.2 秒把"这是一片能玩的地方"这件事说清楚。看过一次后写入 sessionStorage，返回时在 HTML 解析阶段就打上标记，第一帧直接隐藏，不会闪回开场。

（2）点开档案：一场三者同步的转场

点一份档案，球向右滚 90°、抬头、缩小，左栏左滑消失，问诊面板从右滑到中间 —— 三者共用一条 --flow: 1100ms 的时间轴，同一刻停下，球正好趴在面板上边缘。 球的落点不是写死的坐标，而是把面板的 offsetLeft/offsetTop 反投影回 3D 世界算出来的， 换分辨率、换布局都准。转场进度用墙钟计算而不是累加 dt：低帧率设备上 dt 会被钳到 0.05，那样 1.1 秒会被拖成两三秒，球就和面板错开了。

（3）木牌打卡：把"记录"压缩成一个动作

木牌最初只是"看"的 —— 看全家今天吃到哪了。但看和记之间隔着一个二级页面， 而真实场景里用户根本没空跳转。所以现在卡片里每一行药就是按钮： 点一下调打卡接口，成功后重新拉取整块板子，行内状态、表头计数（2/5 → 3/5）、 3D 板面上的字三处同时更新。

这里有个细节值得一提：打卡后同一个人的名字可能因为排序变化而移动，用户会点错行。 所以卡片打开时会把人名顺序冻结下来，打卡只改状态、不重排。

（4）就诊摘要：能带走的那张纸

问诊结束后可以整理成一张 A4 纸：主诉 / 病程 / 在服药与过敏史 / 现在可以先做的 / 何时必须就医 / 想问医生什么。它单独重排了字号和版式（不依赖 flex、色块用真边框）， 用任何工具转 PDF 都不容易变形；同时提供纯文本版，复制到微信里也不会丢掉过敏史。

5.3 看图问诊、管理后台与反馈闭环

（1）看图问诊：图给看得见的模型

用户拍一张皮疹、舌象或药盒发进对话，最初的实现是把 OCR 文本注入提示词，结果文本模型 条件反射地回答"我无法查看图片"—— 它确实看不见。改法不是费力纠正提示词，而是 带图的轮次直接切换 GLM-4V-Flash，把原图转 base64 随消息发出。 视觉信息走视觉模型，文字信息走文本模型，两条路在 lib/ai.ts 一层封装里切换， 业务代码无感。实测端到端回答"是的，我可以看到这张图片……"并正确描述内容。

（2）管理后台：四组九入口的控制台

/admin 是侧栏分组的控制台：数据看板（首页总览、问诊数据报表、AI 效果监控）、 用户与权限（患者管理：检索 / 启用禁用 / 重置密码）、问诊业务（问诊记录：症状输入与 AI 分析结论）、 系统配置与安全（AI 模型配置、系统参数、公告管理、用户反馈、操作日志）。 三个实现细节：

  • 停用即时生效：会话验证时同时检查 disabled，停用账号的旧 Cookie 当场失效， 不等 7 天自然过期；重置密码生成 12 位临时密码，字符集剔除易混淆的 l/1/O/0。
  • 管理员账号受保护：管理接口拒绝操作管理员角色，避免"停用自己把自己锁在门外"。
  • 改配置立即生效：模型参数、平台名称、问诊规则写入 Setting 表（10 秒缓存）， 平台名称全站生效 —— 用户端顶栏、登录页、管理端侧栏、浏览器标签页都读同一份配置。

（3）用户反馈：一条有回音的闭环

用户在「我的」页提交反馈（类型 / 正文 / 满意度星级 / 可选联系方式），提交带限流与最短长度校验； 管理端反馈面板按状态筛选，可以写回复、标记已处理；用户在自己的历史里能看到状态变化和回复内容。 反馈是用户主动写给平台的，后台可读全文；处理动作全部落审计日志。 这个闭环让"收集意见"不是摆设 —— 用户提交后 24 小时内能看到回音，是运营可信度的来源。

5.4 化验单：从一张照片到一张能对比的表

子女拿到父母的化验单，往往只能看懂"有个箭头朝上"，看不懂比上个月是好了还是坏了。 这一块就回答两个问题：哪几项超了、比上次往好还是往坏走。流程四步 —— 上传（复用附件通道）→ 视觉模型抽取 → 代码判异常并合成小结 → 落库并与上一份同类单据逐项对比。

（1）只让模型"抄"，不让它"算"

提示词里写死了边界：只输出项目名、结果、单位、参考区间四项，不做诊断、不给建议。 这样抽出来的是一张表，而不是一段没法比较的话；合规上也干净 —— 模型没有机会说出"提示轻度贫血、建议复查"这类越界判断。

（2）异常判定以算术为准，单据标记只作备选

第一版让模型自己标 abnormal，实测它会把箭头贴错行：白细胞 6.2 明明在 3.5–9.5 之内，被标成"偏低"；真正偏低的红细胞 4.05 反而漏了。于是改成 能算的一律用算术：取结果里的数字、解析参考区间的上下界，超出哪个边界就是哪个方向。 只有定性项目（阴性 / 阳性）或单据没印区间时，才采信模型读到的标记。

小结同理：模型写的那句也数错了（说 3 项异常、把白细胞算进去、漏掉红细胞）， 所以小结改为代码合成 ——"共 8 项，其中 4 项超出参考区间：红细胞计数偏低、血红蛋白偏低、 C 反应蛋白偏高、空腹血糖偏高"。表格标 4 项、小结也说 4 项，两处永远一致。

（3）对比不存库，每次现算

"较上次"是读的时候算的，不落库。原因很实际：患者补传一张更早的单子， 后面几张的对比对象就全变了；存下来只会得到两张卡片各自声称"上次是 5 月"的矛盾。 判断顺序也有讲究 —— 先看异常状态是否翻转，再看数值方向： 血糖从 7.8 降到 6.9（仍偏高）是"在好转"，只看箭头会得出相反结论； 两项都异常时，则比较"离参考区间有多远"，距离缩短记为好转。

实测一份血常规：抽出 8 项、判定 4 项异常；与上一次比，血红蛋白 126 → 118（−6.3%，变差）、 C 反应蛋白 5.2 → 12.4（+138.5%，变差）、空腹血糖 6.2 → 6.8（+9.7%，变差）、 白细胞 6.0 → 6.2（+3.3%，无实质变化）。读不出指标时直接返回 422 并说明换一张更清晰的图， 不留半份脏数据。

项目按"能用 → 好用 → 敢交"三段推进，每一轮都以"自检脚本全绿 + 真实截图"收尾。 代码按模块分 18 次提交入库，提交信息记录每次改了什么、为什么改。

5.6 四个修得比较深的问题

（1）低帧率设备上，转场会错位

最初转场进度是把每帧 dt 累加。但引擎里 dt 被钳到 0.05， 30fps 的机器上 1.1 秒的动画会被拖成两三秒，球和面板就错开了。 改成用墙钟计算进度后，无论多少帧，三者都在同一刻停。

（2）窄屏切回桌面，木牌停在半空

木牌的横向位置取自左栏 .records 的右边界，纵向靠相机反投影。 resize 那一帧里，左栏还是手机版宽度、相机还在插值 —— 两个输入都是旧的，板子就摆错了地方。 修法是在 resize 后记一个 1.4 秒的重排倒计时，逐帧重摆，等 CSS 和相机都落定。 这条后来写成了回归断言（切回桌面木牌必须回到原位，误差 < 24px）。

（3）打包漏掉了 .next/node_modules

分发包解压后 next start 报 Cannot find module。 原因是排除规则里的 node_modules 把 .next/node_modules 整棵剪掉了 —— 那是 Turbopack 给 serverExternalPackages 留的入口（一堆符号链接）。 改法：只剪项目根下的 node_modules，并让遍历跟随符号链接。 这个坑只在"真的解压、真的启动"时才暴露，也是后来坚持做解压验收的原因。

（4）带图提问，模型却说"看不到图片"

用户拍照发进对话，模型回答"我无法查看图片"。排查发现链路本身没断 —— OCR 文本也确实注入了 提示词 —— 是文本模型对图像话题的条件反射式拒答。与其用提示词反复纠正（不稳定、费 token）， 不如换策略：带图的轮次切视觉模型读原图。修复后端到端验证，模型能正确描述照片内容。 顺带把 PRAGMA journal_mode 从 executeRaw 改成 queryRaw （这条语句会返回结果行，用错了每次启动都抛错）。

06　创新点说明

6.1 技术创新点

七条，共同点是把"该确定的"从模型手里拿回来，只在模型擅长的地方用它。

创新点通行做法我们的做法
T1　红旗症状不走模型 把"是否紧急"也交给大模型判断，靠提示词约束 11 条本地正则规则先判，命中即中断问诊并落库。实测拦截 126ms，走模型 1646ms； 模型挂了也不影响这条生命线
T2　冲突判定用代码，不用模型 让模型自己判断"新信息和档案是否矛盾"，容易顺着用户说 diffFacts() 做字段级比对，冲突项默认不勾选、必须人工确认；模型只负责抽取
T3　3D 木牌上贴真字体 把文字烘成贴图，缩放就糊；或者干脆用一块 HTML 浮层假装 板面文字是 HTML，每帧用单应矩阵贴到板子四角 —— 真字体、任意缩放不糊， 还能被子遮挡、跟着板子摆
T4　提醒有两条通道 只依赖系统通知，用户一拒权限功能就废了 先让兔子在草地上说一句、蹦一下，有权限再补一条系统通知；人不在页面上时那句话会存着，回来补上
T5　图文双模型按需路由 固定用一个模型，图片要么不支持要么全走昂贵的多模态调用 纯文字轮次走 GLM-4-Flash，带图轮次才切 GLM-4V-Flash 读原图；切换封装在 AI 层内部， 业务代码无感；没配视觉 Key 时图片退回本地 OCR。成本只花在真正需要"看"的那几轮
T6　工具调用前面加一道"值不值得查" 每句话都先走一轮工具决策，纯聊天也要多等 2~4 秒 先用一组正则做意图门控（吃药 / 漏服 / 能不能吃 / 过敏 / 上次说的），命中了才进 Agent； 进了之后调哪个工具仍由模型自己定。9 条用例逐条验证：该查的查、该直答的直答
T7　同一批工具两种用法 工具写在聊天路由里，只有自家页面能用；或者为外部客户端另写一套 工具的 JSON Schema 只写一份，对话里用 Function Calling、外部用 MCP stdio 导出， 执行共用 runTool()。两种入口的只读边界与按人隔离由同一份代码保证

6.2 应用创新点

五条，共同点是把一个动作的完成成本压到最低，而不是增加功能数量。

创新点通行做法我们的做法
A1　打卡压缩到"一行一次点击" 提醒 → 跳详情页 → 找到那颗药 → 点"已服用" 木牌卡片里每行就是按钮，不进二级页面；打卡后行、表头、3D 板面三处同步。 厨房里一只手也能完成
A2　把问诊变成一张能带走的纸 聊完就结束，复诊时患者凭记忆复述 就诊摘要按 A4 重排版式，可直接打印或复制纯文本；病程时间轴还能铺成投影视图给医生看
A3　一个账号管全家，且互不可见 要么一人一号（老人不会注册），要么全部可见（没有隐私） 一个账号多份档案，越权在 SQL 层挡掉；别人的档案与不存在的档案返回同一个 404， 连"这个 id 存不存在"都问不出来
A4　运营权与隐私边界同时成立 管理后台要么没有（出了问题没抓手），要么能看全部对话（隐私形同虚设） 管理员可停用账号、重置密码、发公告、看统计与 AI 摘要，但接口层就没有对话原文的入口； 用户反馈带回复闭环，意见有去有回；每个后台动作落审计日志
A5　化验单不看箭头，看"比上次" 把化验单当图片存着，或者只做 OCR 转成一段文字 抽出指标后与上一份同类单据逐项对比：哪几项新超标、哪几项在好转、变化多少。 对比每次现算，补传一张更早的单子不会让旧卡片说错话

6.3 与同类作品 / 产品的差异

大部分健康类作品的重心在"功能数量"，MedAI 的重心在"一个动作的完成度"： 打卡是两个动作、问诊是一次点击、复诊材料是一张能打印的纸。 另一条差异是边界感：不诊断、不开方、不替用户判断"哪句重要"， 把 AI 放在"整理和翻译"的位置上 —— 这既是合规要求，也是这类产品能长期被信任的前提。

7.2 安全与隐私

  • 密码 scrypt 加盐哈希；会话是 HMAC 签名的 7 天 Cookie，服务端不存 session 表。
  • 所有读写用一条语句挡越权（findFirst({ where: { id, ownerId } })）， 不做"先查再比对"，避免从响应差异确认某个 id 是否存在。
  • 上传只校验文件头魔数（PNG / JPEG / GIF / WebP），文件名由服务器 randomUUID 生成，不采信用户文件名。
  • 登录限流：按 IP 8 次 / 按账号 5 次，每 15 分钟；成功登录会把计数清零，正常用户不会被误锁。
  • AI 只能读：5 个工具与 MCP 导出的全部是查询，参数里的 patientId 一律按 ownerId 重查， 模型无法通过工具改档案、加药或写结论 —— 写作一律走患者的显式操作。
  • 管理接口统一 requireAdmin() 守卫；注册接口强制 user 角色，无提权入口； 停用账号的旧 Cookie 立即失效；管理员账号不可被停用或重置；后台写操作全部落审计日志。
  • 管理员可见范围收敛：问诊记录只有症状输入与 AI 分析摘要，接口层不存在对话原文的读取入口； 用户反馈为用户主动提交内容，处理动作可追溯。
  • 对话原文保留 30 天，到期清理；小结与结论卡片不受影响。
  • API 密钥只在服务端环境变量，版本库内不含任何密钥（打包脚本会独立复查一次）。

7.4 已知取舍（写在明处）

  • 会话无状态：登出会清 Cookie，但旧 token 在到期前仍可用；要做到即时吊销得加黑名单表。
  • 头像与附件存本地磁盘：单机部署没问题，多实例要换对象存储。
  • SQLite 单文件：适合单机自用，并发写多了要换 Postgres（schema 已备好）。
  • 限流是进程内的：起多实例必须换 Redis，注释里写清了。
  • 首屏 3D 模型 4.7MB：弱网下兔子会晚出现一两秒，有程序化占位体兜底，不会白屏。

08　总结与展望

8.1 做成了什么

七周时间，做了五件事：一个能管全家的档案容器、一个有边界的 AI 问诊、 一个愿意被打开的外壳、一条能运营、能听到回音的通路（管理后台与反馈闭环）， 以及一套能查、能算、能取证的 AI 能力（工具调用、检索与出处、化验单前后对比）。 前两件是功能，第三件是这类产品能不能被用起来的前提 —— 一个需要教三遍才会用的健康 App，老人第二天就不会再点开。

技术上最值得记的不是用了什么框架，而是几条约束： 安全判断不交给模型、冲突判定不交给模型、结论生成不交给模型， 异常项计数与化验小结也不交给模型 —— 能算的都自己算。 这些约束让产品的行为可预测、可解释、可审计，代价是少了几个"看起来很 AI"的功能； 但换来了另一种东西：当模型说"3 项异常"而表格标了 4 项时，我们不需要争论，代码说了算。

8.2 局限

  • 没有真实临床验证：科普内容依据公开诊疗指南与说明书整理，未经过医生评审流程。
  • 红旗规则覆盖有限：11 条规则能拦住最典型的急症表述，但方言、口语化表达仍可能漏判。
  • 单机架构：家庭自用足够，机构规模需要换 Postgres 与对象存储。
  • AI 回答质量依赖上游模型：提示词能约束边界，但不能保证每句话都准确。
  • 检索是词面匹配：BM25 对"我最近老是半夜醒"这类没有关键词的提问命中率低， 此时不硬凑（返回空并让模型说明科普库未覆盖），但也不等于检索到了相关内容。
  • 化验单依赖照片质量：拍歪、反光、被裁切的单据会漏项；我们的策略是看不清楚的不猜， 宁可少一项，也不给一个编出来的数值。

8.3 推广路径

阶段对象怎么用
一、家庭自用有慢病老人的家庭、有小孩的家庭一个账号管全家，免费；核心价值是"今天吃药了没有"和"这次要不要去医院"
二、社区 / 家医签约社区卫生服务中心、家庭医生团队就诊摘要可以直接作为签约居民的随访材料；医生不用再问一遍用药史
三、机构合作药企患者服务、慢病管理公司、养老机构私有化部署（Docker + SQLite/Postgres），数据不出机构

8.4 可持续性

技术上，模型层已经解耦（换厂商只改环境变量），数据层一条 DATABASE_URL 就能切 Postgres， 部署有三条路线（本机 / Docker / Caddy 反代）。 成本上，单用户每次问诊的模型开销是可控的（历史 20 条 + 摘要 3 条 + 结论 8 条的固定上限）， 红旗判断、排程、科普检索全部在本地完成，不产生调用费用。

更重要的是它足够小：不依赖任何第三方健康数据接口，一个 47MB 的离线包解开就能跑。 这意味着它可以被送进网络条件一般的社区医院，而不是只能活在演示视频里。
