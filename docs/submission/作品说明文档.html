一句话说明这个作品在做什么。 MedAI 是一个面向普通家庭的健康档案与 AI 问诊工具：一个账号管全家人的档案，把"该吃什么药、 该不该去医院、复诊时怎么跟医生说"这三件最日常也最容易出错的事，放在一片能点开的草地上。 它不替代医生 —— 只做记录、提醒、翻译和整理。

01　项目背景与意义

1.1 一个被忽略的高频场景

中国有超过 3 亿的慢性病患者，其中相当一部分是老年人；与此同时，"一个家庭里谁在管药"这件事， 通常落在家里那个二三十岁的年轻人身上。他要记得父母各吃什么药、哪天该复诊、孩子发烧到多少度该去医院， 还要在下班后替父母把"医生说的一堆话"翻译成能执行的动作。

这件事的难处不在于信息不够，而在于信息散落在药盒、纸质病历、微信聊天记录和老人的记忆里。 我们做过最朴素的观察：家里老人吃几种药，子女往往说不全；上一次问诊医生说了什么，一周后基本只剩一句"多喝水"。

1.2 现有工具为什么没解决

现有形态它做到的它缺的
手机闹钟 / 药盒提醒器 到点响，便宜、可靠 只知道"该吃药了"，不知道"谁该吃、吃几片、吃没吃"；换个人就全乱
医院 App / 互联网医院 能挂号、能复诊、有电子病历 每家医院一套，跨院不通；面向"这一次就诊"，不面向"这一年"
通用 AI 聊天 什么都能问，门槛低 没有档案就没有个体化；不了解过敏史、在服药物，给出的建议只能停在科普层面
健康管理类 App 功能齐全、数据维度多 要填的太多，老人用不了；界面像体检报告，看不下去

结论是：缺的不是功能，而是一个"全家共用、一个人维护、老人也看得懂"的容器。

1.3 我们想做成什么样

如果一个产品要在深夜被打开、要在厨房油烟里被点一下、要让七十岁的人不用教就会用， 它就不该长得像一套医疗信息系统。所以我们把整套交互放在一片草地上：家里每个人是一块小牌子， 点开就说话；天上吊着一块木板，写着全家今天吃了几次药，点一下就能打卡。 它首先得是个让人愿意打开的东西，其次才是工具。

02　应用场景与目标用户

2.1 用户画像

角色是谁他真正在意的一件事
主要使用者25–45 岁，家里管事的那个子女爸妈今天吃药了没有；孩子夜里发烧要不要去急诊
被照护者父母（多为慢病）、老人、儿童不想学新东西；只想知道"现在该干什么"
次要使用者异地子女、家庭护工不在身边也能看到今天的情况

2.2 三个真实到可以复述的场景

场景一：早上七点，厨房。手机在灶台边响了一声，兔子在草地上说"该给妈妈吃降压药了"。 用户腾不出手，就把手机架起来点了一下木牌上那一行 —— 打卡完成，板子上的 2/5 变成 3/5。 整个过程两个动作，不用进任何二级页面。

场景二：夜里十一点，孩子发烧。用户打开草地，点孩子的牌子问"39 度，一直哭，要不要去医院"。 系统先做本地红旗判断（有没有抽搐、意识不清、皮疹），再结合档案里的年龄体重和在服药物回答， 最后给出一张可以带走的就诊摘要。

场景三：复诊前一晚。用户点开"病程时间轴"，把这三个月发生的事排成一条轴： 哪天开始吃药、聊过几次、结论卡片写了什么。点"投影视图"，铺成一张白纸，截图或打印， 第二天直接给医生看 —— 不用再凭记忆复述。

2.3 使用环境决定了形态

三个场景都发生在手机上，而且经常是"一只手、几秒钟、注意力被打断"的状态。 这直接约束了设计：主操作必须在首屏一次点击内完成；文字要大到在油烟和昏暗里也能读； 动画必须能在中低端安卓机上跑得动（见 5.5 性能取舍）。

03　要解决的实际问题

问题现实里的样子我们的做法
吃了没记 "今天这顿到底吃没吃"—— 老人记不清，子女问不出来，重复服药风险由此产生 天上那块木牌：全家今天的用药一屏看完，每一行就是打卡按钮，点一下记为已服、再点撤销， 行内状态与板面文字同时变

04　产品设计

4.1 视觉与情绪

医疗类产品的默认语言是"白底 + 蓝 + 表格"，它传达的是准确，但也传达距离感。 MedAI 选择的是另一种可信：一片有风的草地、一只毛绒绒的绒球医生、一块手写的木板。 颜色取自清晨的草地（#8abfeb 的天空、#2f4a2b 的深绿、奶油色的纸面板）， 圆角与黏土质感的按钮（.clay）替代了直角卡片。 目的很实际：让人愿意在深夜打开它。

4.2 信息架构

一层内容
草地（首页）家人档案栏 · 今日用药木牌 · 绒球医生 · 疾病科普 / 药品说明两个入口
档案详情基本信息 · 在服药物 · 结论卡片 · 问诊记录（日历） · 病程时间轴 · 成长记录
问诊面板流式对话 · 附件（图片/PDF/Word） · 事实核对 · 就诊摘要
科普库疾病 90 条（13 科室）· 药品 73 种（10 大类）· 症状搜索

4.3 四个关键交互

（1）开场：一株蒲公英

首次进入是一株 186 颗种子的蒲公英（内联 SVG，无图片请求）。吹散之后 3D 草地才显出来 —— 这不是装饰，是用 1.2 秒把"这是一片能玩的地方"这件事说清楚。看过一次后写入 sessionStorage，返回时在 HTML 解析阶段就打上标记，第一帧直接隐藏，不会闪回开场。

（2）点开档案：一场三者同步的转场

点一份档案，球向右滚 90°、抬头、缩小，左栏左滑消失，问诊面板从右滑到中间 —— 三者共用一条 --flow: 1100ms 的时间轴，同一刻停下，球正好趴在面板上边缘。 球的落点不是写死的坐标，而是把面板的 offsetLeft/offsetTop 反投影回 3D 世界算出来的， 换分辨率、换布局都准。转场进度用墙钟计算而不是累加 dt：低帧率设备上 dt 会被钳到 0.05，那样 1.1 秒会被拖成两三秒，球就和面板错开了。

（3）木牌打卡：把"记录"压缩成一个动作

木牌最初只是"看"的 —— 看全家今天吃到哪了。但看和记之间隔着一个二级页面， 而真实场景里用户根本没空跳转。所以现在卡片里每一行药就是按钮： 点一下调打卡接口，成功后重新拉取整块板子，行内状态、表头计数（2/5 → 3/5）、 3D 板面上的字三处同时更新。

这里有个细节值得一提：打卡后同一个人的名字可能因为排序变化而移动，用户会点错行。 所以卡片打开时会把人名顺序冻结下来，打卡只改状态、不重排。

（4）就诊摘要：能带走的那张纸

问诊结束后可以整理成一张 A4 纸：主诉 / 病程 / 在服药与过敏史 / 现在可以先做的 / 何时必须就医 / 想问医生什么。它单独重排了字号和版式（不依赖 flex、色块用真边框）， 用任何工具转 PDF 都不容易变形；同时提供纯文本版，复制到微信里也不会丢掉过敏史。 模型不可用时退回本地模板 —— 绝不空手。

5.2 系统结构

浏览器侧只有一个页面壳：草地 + 档案栏 + 问诊面板，状态都收在 MeadowStage.tsx； 服务端是 24 个 API 路由，按"校验输入 → 认门 → 查配置 → 干活"的固定顺序处理。 AI 调用集中在 src/lib/ai.ts 一层，业务侧不直接碰 fetch。

模块职责
lib/auth.tsscrypt 加盐哈希、HMAC 会话、requireUser()
lib/medical-prompt.ts把档案 / 在服药物 / 摘要 / 结论拼成个体化 System Prompt，带三个 token 上限
lib/red-flags.ts11 条红旗症状正则，命中即中断，不经过模型

lib/visit-sheet.ts就诊摘要的结构、清洗、本地模板与纯文本版（纯函数）

components/meadow/engine.js3D 场景：地形、6 万株实例草、花与蒲公英点精灵、绒球医生、木牌

5.3 AI 这一层：个体化靠提示词，不靠微调

每次对话前拼四样东西：① 档案（年龄、体型、血型、过敏史、病史、习惯、主诉） ② 在服药物 ③ 最近 3 条问诊摘要 ④ 星标优先的 8 条结论。token 靠三个上限恒定， 不会随对话变长而失控。医疗合规三件套永远在场：不下诊断、不开处方； 过敏史优先考虑并主动提醒；涉及处方药必须提示遵医嘱。

失败不留孤儿数据：POST /messages 先调模型，流读完且内容非空， 才把提问和回答一起写库。Key 配错、上游 500、网络中断都不会攒出"只有提问没有回答"的记录。

AI 提建议，患者点头：模型只能返回候选事实（可补字段 / 新增用药 / 与档案冲突）， 一个字不写库；fill 与 add 默认勾选，conflict 默认不勾选并红色高亮， 必须患者亲手确认。冲突判定由代码完成，不交给模型。落库前每条都当不可信输入重新校验： 字段白名单、长度上限、单次 ≤ 20 条、medicationId 按 ownerId 重查。

一条自我约束：结论（Note）不许自动生成。 客观事实可以让 AI 整理，但"哪句重要"是价值判断 —— 只有患者自己知道。 这个取舍让产品少了一个看起来很酷的功能，但保住了"判断权在人手里"这条线。

5.5 性能与稳定性上的几个取舍

  • 连接池压到 1 条（connection_limit=1）：SQLite 写入本来就是整库串行， 连接开多了只会更容易撞 SQLITE_BUSY（全家几台手机同时打卡就是这种场景）。
  • 切 WAL + busy_timeout=5000 + synchronous=NORMAL： 默认模式下一个写事务锁住整库、读只能等；WAL 下读走自己的快照。代价是备份不能用 cp， 已改成 VACUUM INTO 的一致性快照（npm run db:backup）。
  • 渲染上限：devicePixelRatio 封顶 1.5（移动）/ 1.75（桌面）， 并尊重 prefers-reduced-motion —— 关掉动画时场景直接静态。
  • AI 的首包超时：只给"建连 + 首包"设 90 秒上限，拿到响应头就撤计时器。 不能给全程设超时，否则话多的正常回答会被从中间掐断。
  • 登录限流：按 IP 8 次 / 按账号 5 次，每 15 分钟；成功登录会把计数清零， 所以正常用户不会因为反复登录被锁（现场演示连续演练也不会自己把自己关在门外）。

06　实现过程

项目从 10 月中旬开始，按"能用 → 好用 → 敢交"三段推进，每一轮都以"自检脚本全绿 + 真实截图"收尾。 下面的时间线只保留对产品形态有影响的节点。

阶段做了什么为什么这一步重要
第 1 周账号体系、档案增删改查、问诊流式对话、AI 提示词装配先把"能不能用"跑通，此时界面还很朴素
第 2 周3D 草地（实例化草、风摆、绒球医生）、蒲公英开场、点档案的转场产品第一次有了"愿意打开"的理由
第 3 周红旗症状本地规则、事实核对、就诊摘要、问诊日历把 AI 从"聊天"变成"有边界的工具"
第 4 周用药提醒、木牌、病程时间轴、疾病/药品科普库覆盖"吃、看、说"三个真实动作
第 5 周木牌上直接打卡、404/错误页、演示入口、打包与离线部署从"能演示"走到"能交付"

6.1 三个修得比较深的 bug

（1）低帧率设备上，转场会错位

最初转场进度是把每帧 dt 累加。但引擎里 dt 被钳到 0.05， 30fps 的机器上 1.1 秒的动画会被拖成两三秒，球和面板就错开了。 改成用墙钟计算进度后，无论多少帧，三者都在同一刻停。

（2）窄屏切回桌面，木牌停在半空

木牌的横向位置取自左栏 .records 的右边界，纵向靠相机反投影。 resize 那一帧里，左栏还是手机版宽度、相机还在插值 —— 两个输入都是旧的，板子就摆错了地方。 修法是在 resize 后记一个 1.4 秒的重排倒计时，逐帧重摆，等 CSS 和相机都落定。 这条后来写成了回归断言（切回桌面木牌必须回到原位，误差 < 24px）。

（3）打包漏掉了 .next/node_modules

分发包解压后 next start 报 Cannot find module。 原因是排除规则里的 node_modules 把 .next/node_modules 整棵剪掉了 —— 那是 Turbopack 给 serverExternalPackages 留的入口（一堆符号链接）。 改法：只剪项目根下的 node_modules，并让遍历跟随符号链接。 这个坑只在"真的解压、真的启动"时才暴露，也是后来坚持做解压验收的原因。

6.2 工程习惯

  • 所有校验脚本都写成可重复执行的 .mjs / .ts，跑完输出"通过 / 失败"计数，不靠肉眼。
  • 打包红线用代码表达（排除 .env、数据库、上传文件），并在打包后独立复查一遍 —— 排除规则和复查规则不共用同一套窄逻辑，否则一起漏。
  • 交付前不看清单看行为：解压到独立目录 → npm ci → prisma generate → db push → 起服务 → 跑一遍登录、建档、加药、打卡、科普库。

07　创新点与优势

7.1 五个可被检验的创新点

创新点通行做法我们的做法
红旗症状不走模型 把"是否紧急"也交给大模型判断，靠提示词约束 11 条本地正则规则先判，命中即中断问诊并落库。实测拦截 126ms，走模型 1646ms； 模型挂了也不影响这条生命线
冲突判定用代码，不用模型 让模型自己判断"新信息和档案是否矛盾"，容易顺着用户说 diffFacts() 做字段级比对，冲突项默认不勾选、必须人工确认；模型只负责抽取
打卡压缩到"一行一次点击" 提醒 → 跳详情页 → 找到那颗药 → 点"已服用" 木牌卡片里每行就是按钮，不进二级页面；打卡后行、表头、3D 板面三处同步
3D 木牌上贴真字体 把文字烘成贴图，缩放就糊；或者干脆用一块 HTML 浮层假装 板面文字是 HTML，每帧用单应矩阵贴到板子四角 —— 真字体、任意缩放不糊， 还能被子遮挡、跟着板子摆
提醒有两条通道 只依赖系统通知，用户一拒权限功能就废了 先让兔子在草地上说一句、蹦一下，有权限再补一条系统通知；人不在页面上时那句话会存着，回来补上

7.2 与同类作品/产品的差异

大部分健康类参赛作品的重心在"功能数量"，MedAI 的重心在"一个动作的完成度"： 打卡是两个动作、问诊是一次点击、复诊材料是一张能打印的纸。 另一条差异是边界感：不诊断、不开方、不替用户判断"哪句重要"， 把 AI 放在"整理和翻译"的位置上 —— 这既是合规要求，也是这类产品能长期被信任的前提。

8.1 安全与隐私

  • 密码 scrypt 加盐哈希；会话是 HMAC 签名的 7 天 Cookie，服务端不存 session 表。
  • 所有读写用一条语句挡越权（findFirst({ where: { id, ownerId } })）， 不做"先查再比对"，避免从响应差异确认某个 id 是否存在。
  • 上传只校验文件头魔数（PNG / JPEG / GIF / WebP），文件名由服务器 randomUUID 生成，不采信用户文件名。
  • 对话原文保留 30 天，到期清理；小结与结论卡片不受影响。

8.2 已知取舍（写在明处）

  • 会话无状态：登出会清 Cookie，但旧 token 在到期前仍可用；要做到即时吊销得加黑名单表。
  • 头像与附件存本地磁盘：单机部署没问题，多实例要换对象存储。
  • SQLite 单文件：适合单机自用，并发写多了要换 Postgres（schema 已备好）。
  • 限流是进程内的：起多实例必须换 Redis，注释里写清了。

09　推广应用前景

9.1 落地路径

阶段对象怎么用
一、家庭自用有慢病老人的家庭、有小孩的家庭一个账号管全家，免费；核心价值是"今天吃药了没有"和"这次要不要去医院"
二、社区 / 家医签约社区卫生服务中心、家庭医生团队就诊摘要可以直接作为签约居民的随访材料；医生不用再问一遍用药史
三、机构合作药企患者服务、慢病管理公司、养老机构私有化部署（Docker + SQLite/Postgres），数据不出机构

9.2 可持续性

技术上，模型层已经解耦（换厂商只改环境变量），数据层一条 DATABASE_URL 就能切 Postgres， 部署有三条路线（本机 next start / Docker / Caddy 反代）。 成本上，单用户每次问诊的模型开销是可控的（历史 20 条 + 摘要 3 条 + 结论 8 条的固定上限）， 红旗判断、排程、科普检索全部在本地完成，不产生调用费用。

更重要的是它足够小：不依赖任何第三方健康数据接口，一个 47MB 的离线包解开就能跑。 这意味着它可以被送进网络条件一般的社区医院，而不是只能活在演示视频里。
